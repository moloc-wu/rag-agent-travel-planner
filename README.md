# 多日行程规划系统

输入一句话和几个条件，输出一份能照着走的逐日行程：每天去哪几个点、几点到几点、怎么过去、花多少钱。

核心做法是**不把行程交给大模型去"编"**：把行程当成一个带时间窗的多日路径规划问题去求解。

```
高德 Web 服务 ──拉取──▶ 候选 POI + 距离
                            │
自然语言 ──解析──▶ 约束 ──求解──▶ 多日路线 ──校验──▶ 复核结果 ──▶ 页面
```

## 功能

**行程规划**
- 一句话输入（"北京 3 天，预算 2000，喜欢历史文化和自然风光"），也可以只用表单
- 条件：城市 / 天数 / 预算 / 出发日期 / 出发地 / 同行人数（成人·儿童·老人·学生）/ 房型间数 / 餐标 / 兴趣 / 不想要的类型 / 每天几个点 / 硬性时刻锚点 / 休息日
- 结果：统计卡、逐日时间轴（含吃饭和休息时段）、地图路线、费用明细、11 项约束复核
- 两种策略同时给出（纯贪心 / 贪心+局部搜索）并对比，看得出改进在哪

**其余页面**
- 历史方案：保存、改顺序、公开或私密、导出 Markdown / JSON / 打印
- 社区方案：别人保存的公开行程，可点赞、收藏、评论
- 热门榜：按评分和入选次数折算热度排行
- 知识库：上传攻略文本，规划时作为参考片段
- 候选景点：求解器实际能选的全部点
- 管理后台：用户与方案管理（仅管理员可见）
- 游客模式：不注册也能跑一次行程（每分钟限 10 次），保存和历史才需要登录

## 快速开始

**环境**

```bash
python -m pip install -r requirements.txt
```

Python 3.10 以上（用到 `X | None` 类型写法）。依赖只有四条（fastapi / uvicorn / pydantic / pymysql），其余全是标准库；实际跑通的环境是 Python 3.13。

**网页版**

```bash
python server.py
# 打开 http://127.0.0.1:8765
```

首次运行会自动建 SQLite 库（`data/app.db`）；想用 MySQL 见下面「配置」。

**命令行（离线可用）**

```bash
python run_demo.py "长沙2天 预算800 爱吃 9点出发 22点回"
python run_demo.py "北京4日游 预算2000 喜欢历史文化和自然风光" --days 4
python run_demo.py --sample        # 用手工示例数据，完全离线
```

产出 `out/plan.json`（结构化结果）和 `out/demo.html`（单文件页面，双击就开）。

## 配置

**高德 key**

去 [lbs.amap.com](https://lbs.amap.com) 申请「Web 服务」key，写进 `data/amap_key.txt`，或设环境变量 `AMAP_KEY`。只影响"拉取新城市数据"，已经拉好的城市不用 key 也能跑。

**数据库**

默认 SQLite，不用配。要换 MySQL，写 `data/db.json`：

```json
{
  "driver": "mysql",
  "host": "127.0.0.1",
  "port": 3306,
  "user": "root",
  "password": "填你自己的",
  "database": "optw",
  "sqlite_path": "data/app.db"
}
```

MySQL 连不上会自动退回 SQLite 并在控制台说明，服务不会因此起不来。老数据可以用 `python migrate.py` 搬过去。

## 数据

系统支持 **22 个城市**，完整数据下每个城市 24～44 个候选点（合计 554 个），全部来自高德 `/v3/place/text`，含名称、坐标、分类、标签、评分、营业时间、门票。

> ⚠️ **仓库里自带的是精简样本**：`data/cities/<城市>/pois.json` 每城只有 6 条（22 城合计 132 条）。够把流程完整跑通、够离线演示，但排出来的行程会比完整数据单薄不少。
>
> 想要完整数据，二选一：
>
> - **有高德 key**：`python fetch_pois.py --city 北京`，按城市重新拉，会覆盖该城市的样本
> - **自己准备**：把同样格式的 JSON 放进 `data/cities/<城市>/pois.json` 即可，不用改代码
>
> 想先看看密集数据能排出什么，可以打开「候选景点」页——那里列的是当前实际可选的池子，条数就是真实数据量。

| 项 | 情况 |
|---|---|
| 驾车距离 | 只有长沙是实测路网矩阵（44×44），其余城市用坐标直线估算 |
| 门票 | 高德不返回票价，用一张对照表兜底（故宫 60、博物馆 0…），标了来源字段 |
| 闭馆日 | 按类型规则推断（博物馆类周一闭馆），存在 `poi.closed_days`，可以单条改 |
| 酒店 | 每城 15 家左右，含房型与估算房价；房价是估的，不是实时报价 |
| 餐饮 | 每城抓了一批真实餐厅，按距离和人均给出候选 |

新增城市：

```bash
python fetch_pois.py --city 某某市
```

数据落到 `data/cities/<城市>/`，不用改代码。

## 求解

**硬约束（11 条，校验器逐项复核）**

1. 景点时间窗：到达 ≥ 开放，离开 ≤ 关闭
2. 每日时长上限：末站返程后不超过收工时间
3. 总预算：门票 + 餐饮 + 市内交通 + 住宿（＋机动零花）不超过
4. 景点不重复
5. 游览时长充足
6. 单次等开门 ≤ 120 分钟
7. 每天从住宿点出发并回到住宿点
8. 每日体力：点数与累计游览时长上限
9. 必去景点必须进（进不去要说明原因）
10. 闭馆日：不能把周一闭馆的馆排进周一
11. 逐日时间窗：第 1 天从到达算、最后一天到返程截止

**目标**

```
max  Σ 效用(点) − λ × Σ 交通分钟      （λ = 0.8）

效用(点) = 基础热度 × 偏好匹配度
基础热度 = 30 + (高德评分 − 4.0) × 55
```

用户没表态过的标签按 0.55 折价，所以系统不会硬推。

**算法**

1. **贪心**：每轮枚举「未选点 × 每天都 × 每个插入位置」，取「得分增量 / 耗时」最大的可行插入，秒级得到可行解
2. **局部搜索**：在贪心解上做 relocate / swap / 2-opt 三种邻域的首改爬坡
3. **破坏重建**：随机拆掉几个点再用贪心补回，反复几轮，跳出局部最优；固定随机种子，结果可复现

所有中间解都要重新过一遍可行性检查，硬约束绝不放宽。校验器（`verify()`）和求解器是两套独立代码，用来交叉验证。

## 项目结构

| 文件 | 职责 |
|---|---|
| `server.py` | FastAPI 后端：登录注册、规划接口、历史方案、静态前端 |
| `planner.py` | 一次完整规划的编排：召回 → 约束 → 求解 → 复核 |
| `optw_core.py` | 数据模型、交通模型、效用函数、求解器、校验器 |
| `route.py` | 多城市环线（出发地 → 段 1 → 段 2 → 回出发地） |
| `intercity.py` | 城际交通：火车接真实车次，飞机与长途汽车估算 |
| `retrieval.py` | 候选点的召回与重排（词表扩展 + BM25 + 字符 n-gram 向量） |
| `nlparse.py` | 规则版自然语言 → 结构化约束 |
| `cities.py` | 城市索引：哪些城市有数据、住宿点在哪 |
| `store.py` | 存储层：MySQL 优先，SQLite 兜底 |
| `weather.py` | 天气：近期真实预报，远期用历史同期 |
| `fetch_*.py` | 数据抓取：POI、酒店、餐饮、车站、车次、海拔 |
| `web/` | 前端：Vue 3 + Element Plus，依赖全部放在 `web/vendor`，不联网也能跑 |
| `run_demo.py` | 命令行入口 |

## 已知限制

- **仓库自带的是样本数据**：每个城市 6 个候选点，不是完整规模；完整数据要自己拉（见上面「数据」一节）
- **只有长沙有实测驾车距离**，其余城市的行程耗时是直线估的，会偏乐观
- **门票是人工对照表**，覆盖率有限；高德不返回票价
- **酒店房价是估算**，没有接实时房价接口
- **闭馆日靠规则推断**，个别馆的真实规则（比如周二闭馆）没逐个核
- **营业时间是静态窗口**，法定节假日的调整没有处理
- **交通只按驾车时间建模**，没有区分公交和步行

## 说明

前端不引 Node 构建链，组件库和语言包全部下载到 `web/vendor/`，断网也能跑。
登录态不引第三方 JWT 库，用 `base64(uid.exp.hmac_sha256)` 签名，服务端用 `hmac.compare_digest` 校验。
